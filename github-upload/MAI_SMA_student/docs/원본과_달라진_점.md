# 원본(연구 시연판)과 달라진 점

`app/` 의 코드는 연구 시연판(DemoTool)을 빌드 스크립트가 고쳐 만든 것이다. 고친 파일 맨 위에는 "학생 이식판 — 원본: …" 표지와
고친 곳 목록이 주석으로 붙어 있다. **질의 처리(라우터 · 집계형 · 기권 · 절차형 · 인용 검증 · 병기 · 후속 질문)와 모든 프롬프트는
바꾸지 않았다.** 바꾼 것은 LLM 연결, 데이터, 출처 표시, 안내 문구다.

## 1. LLM 연결 — 실행기를 고르게

| 원본 | 학생판 |
|---|---|
| GGUF 모델 파일로 llama-server 를 직접 띄운다(모델 6종 목록 고정) | config.json 의 실행기에 붙는다: Ollama · LM Studio · llama.cpp · 그 밖의 OpenAI 호환 서버 (`app/llm_client.py` · `app/sma_config.py` 새로 만듦) |
| 요청 본문 하나(temperature 0 · top_k 1 · seed 42 · 사고 끔) | preset 별 본문. llamacpp 는 원본과 같고, ollama · lmstudio 는 실행기가 받는 필드만 보낸다. `extra_body` 로 덧붙임 |
| 상태 확인: llama-server `/health` | 모든 실행기 공통 `GET {base_url}/models` |
| — | 오류 해석(인증 · 주소 · 모델 없음 · 문맥 초과 · 지원 안 하는 필드)과 실행기별 조치 안내, `<think>` 덩어리 걷어 내기 |
| — | 이 PC·사내망이 아닌 주소는 `allow_remote: true` 없이는 거부 |
| 중단: 연결을 닫는다 | 같다 + 응답을 기다리는 동안 0.5초마다 중단 요청 확인 |
| START_DEMO.bat · STOP_DEMO.bat | START.bat · STOP.bat · start.sh(duckdb 판 확인 → 설정 → LLM 응답 확인 → 창 없이 기동 → 브라우저). STOP 은 그 폴더의 서버만 끈다(번호표 → 이 폴더의 절대경로) |

설정 창은 GGUF 를 설정했을 때만 헤더에서 제원을 읽고, 아니면 config.json 의 값(실행기 · 주소 · 실제 요청 필드)과 시스템 메모리를 보인다.
모델 제원 계산(`app/model_specs.py`)은 슬라이딩 윈도우 레이어의 KV 헤드 차원을 반영하도록 고쳤다(그런 모델은 상한 ≤ 로 표시).

## 2. 데이터 — 학생용 DB(정비 문서 1,000건)

| 원본 | 학생판 |
|---|---|
| 실제 DB 또는 시연 DB(약 17만 행) | `data/MAI_SMA_학생용DB_1000.duckdb` — 비식별 키트 DB 에서 뽑은 정비 문서 1,000건 + 질의응답 200문항(qa_aggregate · qa_procedural · qa_proc_context) + 프롬프트 원문 |
| 데이터 사전 datadict.txt | `data/datadict_deid.txt`(비식별판 · 123컬럼 — 키트 DB 에 더한 EQUIP_TAG 2열 포함) |
| DB 연결 하나를 여러 요청이 함께 씀 | 요청마다 커서 · 외부 파일·네트워크 접근 차단 · 설정 잠금 · SQL 시간 제한(평가기 run_eval.py 와 같은 방식) |
| 프롬프트 DDL 6개 테이블 | 같다. 학생용 DB 에 더한 qa_* 표는 프롬프트에 보이지 않는다 |
| 규칙 3 의 선박 코드(시연 DB) | 키트의 선박 코드 순열 — `eval/prompts/cond_F.txt` 와 글자까지 같다 |

## 3. 검색 색인과 출처 표시 — 참고 기록

| 원본 | 학생판 |
|---|---|
| 색인 = master 서술 300자 이상 19,990건 | 색인 = 정비 문서 기록 741건(같은 조건) + **참고 기록 305건**(qa_proc_context, 본문 중복 제거) = 1,046건. 토큰화·가중·BM25 식은 그대로 (`app/rag.py` index_rows) |
| 출처 조회: master · pms 에서 선박·기기·호기·장비·문서·담당·정비 항목 | 정비 문서 기록은 같은 값(커서를 잡아 두고 매개변수로 읽게만 고쳤다). 참고 기록은 qa_proc_context 에서 제목 · 기기·호기 · 장비·호기 · 작업일 · 그 본문을 쓰는 문항ID(문항별 묶음)를 채운다 (`app/maintqa_web.py` ref_provenance) |
| 출처 표: 열 머리는 master 기준 하나 | 참고 기록 줄은 qa_proc_context 의 열 이름으로 된 머리행 · 같은 본문 기록의 호기·날짜를 모두 · 문항ID 는 `P063 · records 1–4` 처럼 묶음. 정비 문서 기록 원문 머리에 `synthetic narrative` |
| 출처 표 아래 설명: "master 에서 읽는다 · 본문은 master.WORK_REMARK" | 표에 나온 기록 종류에 맞춰 바뀐다(참고 기록은 qa_proc_context 의 고정 검색 문맥, 정비 문서 기록의 서술은 합성 문장이라는 설명) |
| 화면 모델 이름: GGUF 목록의 이름 | config.json 의 model. 비웠으면(llama.cpp) 실행기 /v1/models 의 id 파일 이름 |
| 사이드바: "19,990 maintenance records indexed" | "1,046 records indexed · 741 documents + 305 reference" |
| /api/info | app · version · preset · base_url · remote · db · docs_ref 를 더했다(START.bat 이 이 프로그램인지 확인) |

## 4. 예시 질문과 첫 화면

`data/demo_questions.txt` 를 이 DB 기준으로 새로 골랐다: 집계형(qa_aggregate, 정답 = answer_text) · 기권 · 절차형(qa_procedural 중 keep=true,
참고 기록에서 답한다) · 정비 문서 기록 예 · 후속 질문 예. 첫 화면 카드는 기권(Q072) · 집계(Q090) · 절차(P022) · 판정 기준(P063).
연구의 퓨샷 예시와 같은 질문은 넣지 않았다(빌드 점검).

## 5. 바꾸지 않은 것

- 라우터 규칙, 집계형 SQL 추출·기권 판정·방언 교정, 절차형 JSON 파싱·인용 검증, 후속 질문 재작성, 병기.
- 모든 프롬프트 글(조건 F · 절차형 답변 · 번역 · 재작성 · 병기). 규칙문 속 통계(73% · 3.21% 등)는 전체 선대 기준 그대로다.
- `app/answer_text.py` · `app/term_map.py` 는 원본과 바이트까지 같다.

## 6. 평가기(eval/)

비식별 키트의 평가기(run_eval.py)를 고쳐 넣었다. 채점·호출 함수 21개는 키트판과 글자까지 같다(빌드 점검).
바뀐 것: 평가 DB(1,000건) · 문항 파일의 정답(이 DB 기준) · 집계형 프롬프트를 템플릿(조건 A · C · F)으로 만듦 · 자체 검사의 기대값 ·
엑셀 기록양식(이 DB 의 qa 표로 새로 만듦). 조건 P · S, 대조판(asrun), 배포 묶음 기능은 뺐다.
결과에 남는 모델 id 는 파일 이름만 남긴다(llama-server 는 GGUF 전체 경로를 id 로 준다 — `chat` 은 그대로 두고 `_chat_student` 로 감쌌다).
자체 검사의 배포 점검은 학생이 만든 `results/` · `responses/` 를 보지 않는다(평가를 돌린 뒤에도 자체 검사가 통과한다).

## 7. 실행 환경 요구

- duckdb 1.5 이상 2 미만(requirements.txt). 2.x 는 relation 의 `fetchone` 이 없어지고, 1.4 이하는 임시 커서 위의 relation 이
  먼저 닫힌다. 이식판의 코드는 커서를 잡아 두고 `execute` 로 읽도록 고쳤지만, 평가기의 키트판 함수까지 같게 지키려고 판을 정해 둔다.
  selftest · check_llm · START.bat · start.sh 가 판을 확인하고 맞추는 명령(`python -m pip install "duckdb>=1.5,<2"`)을 알려 준다.
