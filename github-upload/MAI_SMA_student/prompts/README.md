# prompts/ — LLM 에 보내는 프롬프트 원문

이 폴더의 파일은 **사람이 읽으라고 만든 사본**이다. 실제로 보내는 글은 `app/` 의 코드에 있고, `tools/export_prompts.py` 가
코드에서 이 사본을 다시 쓴다(`--check` 는 어긋났는지만 본다. `tools/selftest.py` 도 확인한다).
프롬프트는 **연구 실험과 같게 두었다** — 학생용 DB(1,000건)로 바꾸면서 고치지 않았다.

## 01 — 집계형 SQL 생성(조건 F)

구성: ① 지시와 DuckDB 방언 안내 ② 스키마(DDL — **6개 데이터 테이블만**: master · pms · consumption · attachments · approval · vessels)와
컬럼 123개의 설명·동의어(`data/datadict_deid.txt` — 연구의 121개 + 16자리 복합코드 EQUIP_TAG 2열) ③ 문서화되지 않은 규칙 12개 ④ 퓨샷 예시 6개 ⑤ 질문 자리 `{q}`.
DDL 은 DB 카탈로그에서 읽어 만들지만 테이블 목록이 고정이라 학생용 DB 의 `qa_*` · `prompt_templates` 표는 모델에게 보이지 않는다.
그래서 이 파일은 `eval/prompts/cond_F.txt` 와 글자까지 같다(17만 행 키트 DB 로 만든 것과도 같다 — 스키마가 같으므로).

**규칙문 속 통계는 전체 선대(17만 행) 기준이다.** 규칙 4 의 "소요시간의 73% 가 1.0 · 상관 0.16", 규칙 6 의 "전체 문서의 3.21% ·
CONS_YN 43건 어긋남", 규칙 11 의 "Y 10,752 / N 40,963" 은 이 DB(1,000건 표본)에서 세면 다르다(소모 기록이 있는 문서 7.5% ·
CRITICAL_YN Y 712 / N 1,584). 규칙은 "어떻게 질의할지"(무엇을 세고 무엇을 기권할지)를 알려 주며, 답의 수치는 늘 이 DB 를 실행한
결과다. 연구와 같은 조건에서 모델을 비교하려고 문구를 바꾸지 않았다. 규칙 3 의 인공 기준일 여섯 짝도 그대로 이 DB 에 들어 있다.

**컬럼 설명(데이터 사전)의 개수·분포도 전체 선대 기준이다.** "MACH_CODE 179종", "EQUIP_CODE 293종 · 2.2% 결측",
"DEPT E=기관부(13,823), D=갑판부(12,728)", "PMS_TYPE CA 43,385 / RH 7,721 / CM 609" 같은 수치는 17만 행에서 잰 값이다.
이 DB 에서는 master 의 MACH_CODE 120종 · DEPT E 550 / D 448 / 빈칸 2 · PMS_TYPE CA 1,864 / RH 400 / CM 32 다.
컬럼 설명은 "그 컬럼이 무엇이고 어떻게 쓰는가"로 읽는다. 개수가 필요하면 이 DB 에서 직접 센다.

평가의 조건 A(스키마만) · C(+ 규칙·퓨샷, 설명 없음)는 `eval/prompts/cond_A.txt` · `cond_C.txt` 다(DB 의 `prompt_templates` 에도 있다).

## 02 — 절차형 답변

검색된 기록 4건(`{ctx}`)과 영어 질문(`{q}`)을 넣어 JSON(`steps`: 단계 · 기록 번호 · 원문 인용, `missing`: 기록이 다루지 않는 것)을 받는다.
`quote` 는 원문을 글자 그대로 옮겨야 하고, 시스템이 원문과 대조해 verified · unverified 를 붙인다.
웹 화면(A)은 영어 단계, 평가기·터미널판(C, 연구 실험의 rag.py ANSWER = `eval/prompts/proc_answer_template.txt`)은 한국어 단계를 받는다.

`{ctx}` 의 기록은 검색 색인(`data/bm25_1000.pkl`)에서 온다. 색인에는 **정비 문서 기록**(master 서술)과 **참고 기록**
(`qa_proc_context`, 절차형 100문항의 고정 검색 문맥 — 실제 정비기록 원문의 가명처리판)이 함께 있다. 두 종류 모두 같은 형식
(`Record n. Title … Machine … Date … 본문`)으로 들어가므로 모델 쪽에서는 구별이 없다. 평가기(`eval/`)는 검색하지 않고 문항마다
정해진 문맥 4건을 그대로 넣는다(연구의 고정 문맥 시험).

## 03 · 04 · 05

- 03 질문 번역: 한국어 질문을 영어로 옮긴다. 설비 용어 대응표(`app/term_map.py`, 82항목)에서 질문에 나온 말의 기록 표기를
  힌트로 주고, 번역문에 그 표기를 덧붙여 검색어로 쓴다(모델 호출 없음). 영어로 물으면 이 단계가 없다.
- 04 후속 질문 재작성: "그럼 발전기는?" 같은 질문을 직전 3턴으로 완결된 질문으로 다시 쓴다. 대화 이력은 이 재작성에만 쓰고
  SQL 생성·답변 프롬프트에는 넣지 않는다(인용 검증이 대조하는 문맥이 흐려지지 않게). 다시 쓴 뒤로는 같은 경로가 돈다.
- 05 병기 번역: 화면 표시용. 검색·SQL 생성에는 들어가지 않는다. 집계형 답 문장의 한국어판은 모델 없이 `app/answer_text.py` 가 만든다.

## 프롬프트를 고치고 싶다면

고치는 곳은 `app/` 의 코드다(이 폴더의 사본이 아니다). 고친 뒤 `python tools/export_prompts.py` 로 사본을 맞춘다.
**평가 결과를 연구·다른 학생과 비교하려면 고치지 않는다** — 고친 프롬프트로 낸 결과는 다른 실험이다.
app/ 의 프롬프트는 웹 화면·터미널판에만 쓰인다. 평가기(`eval/`)는 `eval/prompts/` 의 템플릿과 완성 프롬프트를 쓰므로,
평가에서 바꾼 프롬프트를 시험하려면 그 템플릿을 따로 고치고(`eval/run_eval.py --dry-run --ids Q001` 로 보낼 글을 확인)
결과 태그(`--tag`)에 바꾼 내용을 적어 둔다. 이때 selftest 의 "프롬프트 = 평가기와 같은 글" 점검은 실패한다(의도한 차이다).
